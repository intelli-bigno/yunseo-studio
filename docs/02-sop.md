# 02. SOP — 콘텐츠 3종의 생산 공정과 편성

원문 브리프는 [00-brief-original.md](00-brief-original.md), 콘텐츠 3종·구분 필드·수정 이력은 [01-content-sot.md](01-content-sot.md) §4~6.
화면은 [06-dashboard.md](06-dashboard.md), 시안은 [design/](design/README.md).

한 편 = **피드 게시물 1건**(카드뉴스 1세트)이다. 스토리·하이라이트(「이번 주의 변수」)와 릴스는 피드를 바탕으로 만드는 **파생물**이라 §3·§4 에서 따로 다룬다.
각 단계는 상태(state)이고, 대시보드는 이 상태 기계를 보여주고 움직인다.

```
idea → selected ─┬→ drafted → verified → rendered → in_review ─┬→ approved → scheduled → published → measured
                 │                                              └→ changes_requested → (drafted | verified | rendered)
                 └→ waiting_evidence → drafted            (② 이슈 이후 전용: 자료가 모일 때까지 대기)
```

- 릴스 확장(`reels_ready`)은 `published` 뒤 또는 `approved` 와 나란히 도는 **선택 가지**다(§4).
- 이전 상태 이름에서 `shorts_ready` 는 `reels_ready` 로 바꿨다. 코드에는 아직 쓰이지 않는다.

## 1. 사람 게이트 — 3곳 (최종 브리프 6절)

운영자가 맡는 일은 **주제 선정 · 핵심 관점 · 사실 확인 · 최종 발행 판단**이다. 나머지는 가능한 범위에서 자동화한다. 사람 게이트는 이 네 가지에 맞춰 세 곳이다.

| 게이트 | 상태 전이 | 운영자가 하는 일 | 자동화가 하는 일 | 통과 기록 |
| --- | --- | --- | --- | --- |
| **G1 주제·관점** | `idea → selected` | 주제 선정, **핵심 관점**(왜 이 사건인가·무엇을 말할 것인가) 한 문장, 중요도 판정 | 후보 수집, 점검표 미리 채우기 | 선정자·시각·`importance`·핵심 관점 한 문장 |
| **G2 사실 확인** | `drafted → verified` | claim 별 출처·원문 대조, 해석이 사실 위에 서 있는지 확인, ②는 `evidence_ready` 판단 | 출처 칸 누락·링크 열림·수치-claim 대응 검사 | claim 별 `verified_by`·`verified_at` |
| **G3 최종 발행 판단** | `in_review → approved` | 체크리스트(§5)로 최종 판단, 승인/반려(사유 필수) | 금지 표현·규격·자리표시자 검사 | 승인자·시각·산출물 해시 |

- 그 밖 단계는 자동이되, 실패하면 멈추고 사람에게 알린다.
- **승인 뒤 산출물이 바뀌면 승인은 자동 무효**다(수정 이력 §6 규칙과 같은 원칙).
- [L9] 승인본(`approved`)도 **수정 요청**(`changes_requested`, 사유 필수)으로 작성 단계로 되돌릴 수 있다 — 승인은 무효가 되고 이력에 사유가 남는다. 코드는 상태를 따로 두지 않고 `drafted` 로 돌린다(04 상태 기계).
- [L9] G2·G3 의 자동 검사는 렌더 전 검사와 같은 규칙이다 — 게이트를 지난 편이 렌더에서 막히지 않는다.
- 자동 초안(`drafted_by: assistant`)은 G2 전에 사람이 저장해야 `operator` 가 된다.

| --- | --- | --- | --- | --- |
| 1 | **소재 선정** (G1) | 캘린더 후보·연구 backlog → 선정된 1건 | 사람 (자동은 후보만) | 종류(①②③)·주제·핵심 관점 한 문장·`importance`·게시 예정 시각 |
| 2 | **자료 수집·정리** | 선정 건 → 자료 묶음(1차 자료 우선) | 자동 + 사람 | 출처 후보 목록, 사건 일정·시간대 확인 |
| 3 | **원고** | 자료 + 포맷 → 단별 원고 + 운영자 해석 | 사람 (자동은 초안) | 단 전부 채움(스키마 통과), 구분 필드(`kind`·`basis`)·`as_of` 입력, 금지 표현 block 0 |

| 5 | **카드 렌더** | 검증된 원고 + 시각 프리셋 → PNG | 자동 | 규격 검사 통과, 글자 넘침 0, `TBD` 잔존 0 |
| 6 | **검수** (G3) | 카드·캡션·출처 표 → 승인/반려 | **사람** | 체크리스트 전 항목 + 승인 기록 |

| 8 | **성과·복기 기록** | 게시물 ID → 지표 시계열 + 복기 메모 | 자동 수집 또는 수동 | 게시 후 24h·7d 기록, ②는 이전 편 대비 메모 |

### 단계 보충

**1. 소재 선정** — 선별이 가치다. 모든 일정을 다루지 않는다. 중요도 판정은 §3.2.
복잡한 사건이면 배경 설명 편을 선행한다. 같은 유형의 직전 게시물과 논지가 겹치면 경고한다(회차 대장 원칙).

**3. 원고** — 정본은 YAML(자유 텍스트 아님)이다. 렌더·릴스·캡션이 같은 원고를 쓴다(사본 금지).
LLM 초안은 항상 `drafted_by: assistant` 로 표시한다. [결정 필요 D4 — LLM 사용 여부·비용]

**4. 사실·출처 검증** — 출처 우선순위는 1차 자료(중앙은행·통계청·선관위·기업 공시) > 주요 언론 > 기타.
`market_expectation`·`market_reaction` 의 가격 수치는 분 단위 `as_of` 를 남기고 **게시 직전 재확인** 대상으로 표시한다.
자동 검사는 「칸이 비었는가」「URL 이 열리는가」까지만 한다. **내용 일치 판정은 사람이 한다.**

**5. 카드 렌더** — HTML/CSS 템플릿 + 프리셋 → 로컬 렌더로 PNG(로컬 파일 렌더는 허용 범위).
검사: 비율·해상도, 텍스트 넘침, 대비(접근성), `TBD` 잔존, 표지가 이전 게시물과 같은 틀인지.

**7. 게시** — D2 로 확정: MVP 는 **수동 업로드 묶음**, M3 에 IG API + YT 비공개 업로드.

## 3. 편성 규칙 (최종 브리프 5절)

### 3.1 채널별 주기

| 채널 | 주기 | 내용 | 비고 |
| --- | --- | --- | --- |
| **피드** | **하루 1개** | 중요 사건 전후(①②) 우선, **나머지 날은 ③ 트레이딩 연구** | 1개는 리듬이지 채워야 하는 할당량이 아니다(§3.3 쉬는 날) [해석 — 결정 D14] |
| **스토리·하이라이트** 「이번 주의 변수」 | **주 1회** | 이번 주 사건·변수 목록. **날짜(요일·시간대)가 한눈에 보인다** | 하이라이트는 최신본으로 교체하고 지난 주는 날짜를 남겨 보관. 발행 요일 [결정 D15] |
| **릴스** | **주 1~2개** | 그 주 피드 중 **시각 설명이 좋은** 주제를 확장 | 새 주장을 더하지 않는다(§4) |

### 3.2 중요도 판정 (G1, 사람이 한다 — 자동은 점검표만 채운다)

사건 하나에 아래 다섯 가지를 예/아니오로 답한다.

| # | 질문 | 이유 |
| --- | --- | --- |
| a | **기대 변화** — 결과에 따라 시장의 기대가 실제로 바뀌는가 | 선별의 핵심 |
| b | **갈림** — 시나리오가 둘 이상으로 갈리는가 | 시나리오 규칙(편집 원칙 2) |
| c | **자료** — 1차 자료와 사전 시장 기대를 확인할 수 있는가 | 출처 규칙, 「충분한 자료 확보」 |
| d | **해석** — 운영자가 얹을 도메인 해석이 있는가 | 차별점 |
| e | **후속** — 결과 뒤에 확인할 변수가 남는가 | ② 이후 편의 가치 |

| 판정 | 조건 | 편성 |
| --- | --- | --- |
| **`major`** | a·b·c·d 모두 예 | ① 이전 편 편성. e 가 예면 ② 이후 편도 계획(`post_planned`) |
| **`watch`** | a 또는 b 가 예, c·d 중 하나 이상 아니오 | **피드 편성 없음.** 「이번 주의 변수」에만 오른다. 자료가 모이면 `major` 로 승격 가능 |
| **`skip`** | 그 밖 | 다루지 않는다 |

- 판정 기준(예/아니오의 문턱)은 처음 4주 운영 기록으로 조정한다. 조정 시 이유를 남긴다. [미검증 — 가정]
- 구현(L4): 자동 수집이 채우는 점검표는 일정 **종류별 기본값**이고(`packages/domain/src/events/importance.ts`), d(운영자 해석)는 사람만 알아서 항상 「아니오」다 — 그래서 자동 제안은 `watch` 이하이고 `major` 는 사람이 사유와 함께 올린다. a·b 중 하나만 예인데 c·d 가 모두 예인 경우는 표에 없어 `watch` 로 둔다 [해석].
- **발행량을 채우려고 판정을 올리지 않는다.** 판정을 올릴 때는 사유(어떤 질문의 답이 왜 바뀌었는가)를 기록한다.

### 3.3 피드 슬롯 배정 (하루 1개)

날짜 D 의 피드를 위에서부터 첫 번째로 맞는 것으로 채운다.

1. **D+1 에 `major` 사건이 있다** → ① 이전 편 (기본 전날 발행). 복잡하면 배경 설명 편을 며칠 앞서 낸다.
2. **지난 `major` 사건의 ② 이후 편이 `evidence_ready`** → ② 이후 편.
3. 그 밖 → ③ 연구 편 (진행 중인 스레드의 다음 단계, 없으면 backlog 에서).
4. **③ 중 `verified` 된 것이 없거나 기준에 못 미친다 → 발행하지 않는다.** 쉬는 날은 정상이며 사유를 기록한다(`skipped_slot`). `watch`/`skip` 사건을 키워 채우지 않는다.

충돌 규칙:
- 같은 날 ①이 둘 이상 → 우선순위 `major` 중 중요도가 높은 한 건만 피드에, 나머지는 스토리 「이번 주의 변수」로 노출하거나 하루 당겨 발행한다. (우선순위 ① > ② > ③)
- ②가 3일 넘게 `evidence_ready` 가 못 되면 운영자가 판단한다: 계속 대기 / 스토리 한 줄로 대체 / 취소. 서두르지 않는다.
- ②는 **속보 경쟁이 아니다.** 기한은 없고 자료 확보가 먼저다.

### 3.4 스토리 · 하이라이트 「이번 주의 변수」

- 주 1회, 그 주의 `major` + `watch` 사건을 날짜순으로 나열한다. **날짜·요일·시간대**가 가장 크게 보인다.
- 각 줄 = 사건명 + 「무엇이 변수인가」 한 줄(해석이면 해석 표시). 일정의 출처는 공식 일정 기관의 캘린더다.
- 일정이 바뀌면 조용히 고치지 않고 수정 이력(01 §6)을 남긴다.
- 지난 주 항목은 「이후 편 링크」로 닫는다 — 이전↔이후 연결의 입구가 된다.

## 4. 릴스 확장 (주 1~2개)

- **선정**: 그 주 `verified` 된 피드 중 시각 설명 점수가 높은 것 — 흐름도·차트·전후 비교가 이미 있는 카드를 우선. 점수는 사람이 매기고 자동은 후보만 낸다.
- **원고**: 피드 `verified` 원고의 범위 안에서만 만든다. 새 주장·새 수치를 더하지 않는다(더하려면 피드 원고부터 `verified`).
- **형식**: 세로 9:16, 자막 중심, 음성 없음이 기본 [결정 D6]. 길이는 15~45초 [미검증 — 첫 편 뒤 조정].
- 출처는 영상 설명란에 같은 출처 표를 붙인다. YouTube Shorts 에 같은 영상을 재사용할지는 [결정 D16].

### 4.1 합성 규격 (L3, 2026-11-05)

카드 세트(`CardRenderResult`) → `1080×1920` MP4 + SRT. 값은 한 곳(`packages/domain/src/reel/preset.ts` 의 `DEFAULT_REEL_PRESET`)이고, 첫 편을 올려 본 뒤 이 값만 고친다. 장면 계획·배치·SRT 는 순수 함수(`packages/domain/src/reel/`), ffmpeg 호출은 어댑터(`packages/adapters/video`), 명령은 `apps/cli` 의 `reel`.

| 항목 | 기본값 | 근거 |
| --- | --- | --- |
| 출력 | 1080×1920 · 30fps · H.264(High, yuv420p, bt709) + AAC | 9:16 세로. 합성 직후 ffprobe 로 해상도·코덱·길이를 검사하고 어긋나면 실패 |
| 전체 길이 | 15~45초 | 위 §4 의 가정 [미검증 — 첫 편 뒤 조정]. 벗어나면 합성하지 않고 이유를 알린다 |
| 카드별 노출 | 1.2초 + 자막 글자 수 ÷ 14자/초, 3~6초. 전체가 15초에 모자라면 장면당 8초까지 늘리고, 45초를 넘으면 3초까지 줄인다 | 소리 없이 짧은 문장을 읽는 속도 가정 [미검증] |
| 전환 | `crossfade` 0.5초(기본) · `dip`(검은 화면 경유) 0.6초 · `slide` 0.4초 · `cut` | 자막은 카드가 온전히 보이는 구간에서만 뜬다(전환 중에는 없음) |
| 안전영역 | 위 270 · 아래 380 · 좌우 64 px | 계정·캡션·버튼이 가리는 영역을 알려진 권고치(위 14%·아래 약 20%·좌우 6%)로 가정 [미검증 — 플랫폼 공식 문서는 Aside 로 열람해 확인 필요] |
| 배치 | 안전영역 위쪽에 4:5 카드를 가장 크게(826×1034), 그 아래에 자막 상자. 뒤 배경은 같은 카드를 흐리고 어둡게 | 새 색을 만들지 않는다 |
| 자막 | 카드 대체 텍스트(`altTexts`)의 첫 문장, 최대 3줄. 흰 글자 + 반투명 검은 상자. SRT 는 항상 내고 번인은 끌 수 있다 | 줄이 넘치면 절 단위로 잘라 경고(`reel/subtitle-truncated`) — 의미가 바뀌지 않았는지 사람이 본다 |
| 오디오 | **무음 AAC 트랙**(48kHz 스테레오)이 기본. 음성·음악은 파일 경로를 줄 때만 섞는다(음악은 반복, 기본 −18dB) | D6 자막만. 오디오 스트림이 없는 파일을 이상하게 다루는 업로드 경로 대비 + 나중에 음성을 얹어도 규격이 같다 [미검증] |
| 서체 | 실행기에 있는 `DejaVu Sans`(브랜드 서체 미정). 실행기에는 한글 서체가 없다 | 영어 발행이 기본(D10). 한글 자막은 서체를 설치하고 `--covers-hangul` 로 확인을 알려야 경고가 사라진다 |

- 실행: `win auto -- pnpm exec tsx apps/cli/src/main.ts reel <cards-dir> --out <dir>`. `<cards-dir>` 에 `render-result.json`(`CardRenderResult`)이 있으면 그 순서·대체 텍스트를 쓰고, 없으면 `*.png` 를 이름순으로 읽는다.
- ffmpeg 는 Windows 실행기에 이미 있다(`/usr/bin/ffmpeg` 6.1.1 — libx264·libass·xfade 확인, 2026-11-05). 없는 환경에서는 건너뛰지 않고 「ffmpeg 를 실행할 수 없다 …」로 실패한다.
- 음성·음악 자리: `--voice`·`--music` 또는 `createFfmpegReelComposer({ tracks })`. TTS·유료 API 는 연결하지 않았다(D6 ②③ 은 성과 실측 뒤).

## 5. 단계별 체크리스트

### 5.1 G1 — 소재 선정
- [ ] 종류(① ② ③)와 한 줄 질문이 정해졌다
- [ ] 중요도 a~e 판정 + `major`/`watch`/`skip` (①②)
- [ ] 핵심 관점이 한 문장으로 적혀 있다 — 자료 요약이 아니라 **운영자가 보는 것**
- [ ] 게시 예정 시각(시간대 포함) — ①은 사건 전날, ②는 `evidence_ready` 이후, ③은 비어 있는 날
- [ ] ②: 가리킬 이전 편이 있다(없으면 「사전 시나리오 없음」 표시)
- [ ] ③: 스레드 id 와 단계(`stage`)가 정해졌다

### 5.2 G2 — 사실 확인
공통
- [ ] 모든 claim 에 `kind`·`basis`·`as_of` 가 있다, 한 문장에 `kind` 하나
- [ ] `fact`·`market_reaction`: 출처 URL·접근일·**원문 인용**, 사람이 원문과 대조했다
- [ ] 해석·시나리오가 `based_on` 으로 사실에 닿아 있다
- [ ] 직접 경험은 `experience` 로 표시되고 조사 내용처럼 쓰이지 않았다
- [ ] 편 전체 `as_of` 가 claim 들의 가장 늦은 `as_of` 이상이다
- [ ] 가격·시장 수치는 게시 직전 재확인 표시가 있다

종류별 추가
- [ ] ①: 시나리오 둘 이상, 단마다 질문에 답한다, 「확인할 것」에 볼 곳이 있다
- [ ] ②: `evidence_ready` 4항(01 §4.3) 충족, 이전 편 시나리오 **전부**에 `scenario_outcomes`, 「확인할 것」 항목 전부 `check_results`
- [ ] ②: 바뀐 판단은 `judgment_update` 에 이유가 있고 이전 편 수정 이력과 연결됐다
- [ ] ③: `limits`(적용 조건·한계)와 `verified_scope`(실제 검증 범위)가 비어 있지 않다
- [ ] ③ 도구 편: 게시물 안에서 사용법이 끝난다, 배포 안내는 마지막 한 줄 이하
- [ ] ③ 성과 수치: 표본·기간·비용 가정이 같이 있고 앞날을 단정하지 않는다

### 5.3 G3 — 최종 발행 판단
- [ ] 투자 권유로 읽히는 문장 없음 (명령형 매수·매도, 수익 확약, 특정 종목 추천), 수치 단정 없음
- [ ] 금지 표현 검사 통과 (block 0, warn 은 사람이 읽고 판정)
- [ ] 사실 / 시장 반응 / 해석 / 시나리오가 화면에서 구분돼 보인다
- [ ] 출처 카드와 기준 시점이 있다
- [ ] 이벤트 일시·시간대 정확, 오늘 기준으로 재확인함
- [ ] 브랜드 자리표시자 없음, 고지 문구(확정본) 포함
- [ ] 맞춤법 (발행 언어 기준)
- [ ] 표지가 이전 게시물과 같은 틀, 차트는 한눈에 읽힘
- [ ] ②: 이전 편과 나란히 읽었을 때 모순이 없다(달라진 부분은 이유가 적혀 있다)
- [ ] 이 편을 내는 이유가 「채우려고」가 아니다

### 5.4 스토리 「이번 주의 변수」
- [ ] 각 줄에 날짜·요일·시간대, 일정 출처
- [ ] 변수 한 줄이 사실인지 해석인지 표시
- [ ] `watch` 를 `major` 처럼 보이게 쓰지 않았다
- [ ] 지난 주 항목은 이후 편 링크로 닫았거나 닫지 못한 이유가 있다

### 5.5 릴스
- [ ] 원본 피드가 `verified`·`approved` 이고 새 주장이 없다
- [ ] 자막이 안전 영역 안, 소리 없이 이해된다
- [ ] 출처 표를 설명란에 붙였다
- [ ] 표지 프레임이 피드와 같은 틀

## 6. 자동화 ↔ 운영자 책임 경계

| 일 | 자동화(가능한 범위) | 운영자 |
| --- | --- | --- |
| 자료 수집 | 공식 일정·공개 API·파일 원천 수집, 출처 후보 정리 | 어떤 자료를 믿을지 정함 |
| 일정 정리 | 캘린더 후보 → 「이번 주의 변수」 초안 | 중요도 판정, 최종 목록 |
| 초안 | 단별 초안·문장 다듬기(`drafted_by: assistant`) | **핵심 관점**, 운영자 해석 작성, 저장 |
| 사실 확인 | 빈 칸·링크·수치-claim 대응 검사 | **원문 대조와 확인 기록** |
| 디자인 | 카드·표지·차트 렌더, 규격·넘침 검사 | 표지 일관성·가독성 눈 확인 |
| 릴스 | 후보 점수, 자막 합성 | 선정, 승인 |
| 게시 | 업로드 묶음 생성(MVP) → 예약 호출(M3) | **최종 발행 판단**(승인) |
| 정정 | 이력 기록, 승인 무효 처리 | 수정 이유 작성, 후속 설명 |
| 성과 | 지표 수집·표 | 해석, 편성 조정 |

원칙: **자동화는 사람 게이트를 대신 통과하지 못한다.** 게이트 기록이 없으면 다음 상태로 못 간다(도메인 규칙으로 막고 테스트한다).
