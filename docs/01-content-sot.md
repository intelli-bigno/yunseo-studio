# 01. 콘텐츠 정본(SoT, Source of Truth)과 프리셋

원문은 [00-brief-original.md](00-brief-original.md) 에 그대로 보존했다. 이 문서는 그 정리본이다.
원문과 다르게 읽히면 원문이 맞다.

## 1. 원칙

- **바뀌지 않는 것(편집 정본)**과 **바뀌는 것(프리셋)**을 파일로 나눈다.
- 브랜드 이름·캐릭터·발행 언어는 아직 미정이다. 코드·템플릿은 이름을 직접 쓰지 않고 프리셋 키만 참조한다.
  확정되면 **프리셋 파일 교체만으로** 전 게시물·대시보드에 반영된다.
- 정본은 Git 에 있는 텍스트 파일(YAML)이다. DB 는 정본을 복제하지 않고 "어느 프리셋 버전으로 만들었나"(버전 해시)만 기록한다.

## 2. 편집 정본 (확정 — 바꾸려면 사람 승인)

| 항목 | 값 |
| --- | --- |
| 컨셉 | 세계의 변화와 시장을 연결하고, 다가올 사건의 파급효과를 미리 짚는 투자 매거진 |
| 핵심 문장 | 세계의 변화에서, 시장의 다음 질문을 찾습니다. |
| 다루는 것 | 주요 경제·정치 이벤트의 시나리오와 시장 영향, 트레이딩 관점, 연구 |
| 차별점 | 자료 조사에 **운영자의 도메인 지식·경험**을 더해 고유 해석을 쌓는다 |
| 최우선 목표 | **팔로우하고 싶은 매체** — 팔로워가 "좋은 정보원을 알고, 흐름을 읽고, 자기 관점으로 판단하는 사람"처럼 느끼게 한다 |
| 브랜드 인상 | 차분함 · 안목 · 신뢰감 · 접근성. 읽기 쉽되 새로운 연결과 생각할 거리를 준다 |
| 알파(차별 가치) | 많이 말하기가 아니라 **선별과 해석의 깊이** |
| 타겟 | 국가가 아닌 **관심사·태도**로 정의한다 — 경제·정치·시장 흐름에 관심 있고, 자기 판단 기준을 만들고 싶은 독자. 한국 한정 아님 |
| 팔로우 이유 (최종 브리프 7절) | 다가올 사건을 **미리 생각**하고, 결과 뒤 **판단을 점검**하며, 평소엔 **직접 활용할 관점과 도구**를 쌓는다 — 「좋은 소스를 알고, 시장을 자기 관점으로 읽는 사람들의 매거진」 |
| 콘텐츠 3종 | ① 이슈 이전 ② 이슈 이후 ③ 트레이딩 연구 → §4 |
| 운영 리듬 | 피드 하루 1개 · 스토리/하이라이트 「이번 주의 변수」 주 1회 · 릴스 주 1~2개 → 편성 규칙은 [02-sop.md](02-sop.md) |
| 초기 목표 | 프로필과 최근 게시물만 보고도 관점·취향이 느껴져 팔로우 |
| 이후 목표 | 사건 전후 분석·연구로 재방문 · 저장 · 공유할 이유를 만든다 |
| 시각 | 절제된 색 · 선명한 타이포 · 읽기 쉬운 차트 · 일관된 표지 |
| 발행 언어 | **미정** — 프리셋 값. 기본값은 영어(이전 전달)이며 사용자 확정 전이다 → [결정 D10] |
| 채널명·최종 시각 디자인 | **미정** — 위 「팔로우 이유」 방향을 기준으로 나중에 확정 → [결정 D5·D13] |

### 금지 표현 (확정 — 데이터는 `presets/compliance/banned-expressions.yaml`)

| 표현 | 적용 범위 | 처리 |
| --- | --- | --- |
| 「무료」 「수익 보장」 「비밀 정보」 「무조건」 | 본문·캡션·카드·브랜드 문구 전부 | block (게시 불가) |
| 「지표」 | **브랜드 전면 홍보 문구**(이름·소개·한 줄 설명 등)만. 본문에서는 일반 용어로 쓸 수 있다 | block |
| 위 표현의 영어 대응(예: guaranteed return, insider information) | 발행 언어가 영어일 때를 대비한 **제안** | warn — 사람이 확정하기 전까지 막지 않고 알린다 → [결정 D11] |

검사는 코드(`packages/domain` 의 `findBannedExpressions`)와 테스트로 강제한다. 공백·전각·제로폭 문자로 피할 수 없게 정규화해서 비교한다.

### 편집 원칙 (정본에서 도출 — 검수 체크리스트로 쓴다)

1. **해석을 주되 결론을 강요하지 않는다.** "사라/팔아라"가 아니라 "이 신호가 나오면 이렇게 읽을 수 있다".
2. **시나리오는 항상 둘 이상.** 한 방향 예측 금지. (스키마가 강제)
3. **모든 수치·사실은 출처가 있다.** 출처 없는 수치는 `verified` 로 못 올라간다. (스키마가 강제)
4. **독자가 손에 쥘 것 하나.** 발표 이후 직접 확인할 신호·자료 하나 이상. (5단 중 마지막 단)
5. **운영자 해석을 비워 둔 채 검수로 보내지 않는다.** 자료 조사만으로는 차별점이 없다. (스키마가 강제)
6. **투자 권유로 읽힐 수 있는 표현은 검수 게이트에서 사람이 판정한다.** 고지 문구는 아직 미확정이다 → [결정 D8]
7. **사실 · 시장 반응 · 해석 · 시나리오를 섞지 않는다.** 직접 경험과 조사 내용도 섞지 않는다. (§5, 스키마가 강제)
8. **출처와 기준 시점이 없는 주장은 내보내지 않는다.** (§5)
9. **판단이 달라지면 숨기지 않는다.** 후속 게시물에서 수정 이유를 설명한다. (§6)
10. **도구·연구는 적용 조건 · 한계 · 실제 검증 범위와 함께 낸다.** 홍보보다 게시물 안의 가치가 먼저다. (§4.4)
11. **작은 사건을 키우지 않는다.** 발행량을 채우려고 중요도를 올리지 않는다. (02 편성 규칙)

## 3. 프리셋 (교체 가능)

```
presets/
  active.yaml                         지금 쓰는 조합 (파일 경로만 가리킴)
  brand/brand.default.yaml            이름·핸들·컨셉·핵심 문장·색·서체·로고·시각 규칙
  character/character.default.yaml    화자 형태(미정)·말투·외형 참조
  tone/tone.default.yaml              목소리·원칙·읽기 수준·이모지
  language/language.default.yaml      발행 언어(기본 en, 미확정)·운영자 UI 언어
  format/pre-issue-5.yaml             포맷 ① 이슈 이전 (5단, 카드 7장)
  format/post-issue-4.yaml            포맷 ② 이슈 이후 (4단)
  format/research-5.yaml              포맷 ③ 트레이딩 연구 (스레드 5단계)
  compliance/banned-expressions.yaml  금지 표현 규칙 데이터
```

- 모든 프리셋은 스키마(`packages/presets-schema`)로 검증한다. 필드 누락·형식 오류면 로드가 실패한다.
- `active.yaml` 만 바꾸면 조합이 바뀐다. 로드 결과에는 프리셋 파일 내용의 sha256(`versionHash`)이 붙는다.
- **자리표시자(`TBD`)**: 이름·핸들·서체·강조색·로고·화자 이름이 미정이라 값이 `TBD` 다. 하나라도 남아 있으면 `validate --publish` 가 실패한다(게시 단계 차단 규칙).
- 색은 잠정값(흰 배경·검정 글자·회색·강조색 TBD)이다. 브랜드 확정 때 교체한다.

### 화자 (character)

화자 형태 자체가 미정이다: ①최윤서 본인 얼굴·이름 ②캐릭터(일러스트·AI) ③익명 에디터 목소리. → [결정 D7]
프리셋은 `kind: undecided | person | illustrated | editor` 로 담는다.

## 4. 콘텐츠 3종

최종 브리프(7절)로 포맷이 셋이 됐다. 셋은 **하나의 흐름**이다 — 사건 전에 생각하고(①), 결과 뒤 판단을 점검하고(②), 평소엔 직접 쓸 관점과 도구를 쌓는다(③).

| 종 | 형식 id | 한 줄 질문 | 언제 | 상태 |
| --- | --- | --- | --- | --- |
| ① 이슈 이전 | `pre-issue-5` | 이 사건을 어떻게 미리 생각할까 | 사건 **전날**(복잡하면 배경 설명 편 선행) | 활성 — 코드 스키마·프리셋·카드 렌더 |
| ② 이슈 이후 | `post-issue-4` | **무엇이 달라졌는가** | **충분한 자료를 확보한 뒤**(속보 경쟁 아님) | 활성 — 코드 스키마·프리셋·카드 렌더 |
| ③ 트레이딩 연구 | `research-5` | **어떻게 판단하고 실행할 것인가** | 이슈 없는 날 | 활성 — 코드 스키마·프리셋·카드 렌더 |

> 이 절의 ②·③ 필드 표가 **정본 설계**이고, 코드는 `packages/domain/src/content/`(`post-issue.ts`·`research.ts`)·`presets/format/`(`post-issue-4.yaml`·`research-5.yaml`)에 옮겼다(2026-11-05).
> 세 종은 같은 진입점으로 읽는다 — `validateContentDoc(input)`(스키마 식별자로 분기), 렌더 전 검사 `contentBlockers(body, rules)`(금지 표현·글자 상한·출처/기준 시점 → `block`/`warn`).
> 파일 필드 이름은 YAML 그대로(snake_case)이고 claim 은 평평하다: `source_url`·`accessed_at`·`quote`·`publisher`·`tier`(출처), `kind`·`basis`·`as_of`(구분), `based_on`·`condition`·`experience`.
> **봉투 필드**(`as_of`·`importance`·`reels`·`revisions`·`type`)는 예전 파일에 없어도 읽는다(없으면 null·빈 배열). draft 에서는 비어 있어도 되고 `verified` 에서만 막는다.
> 본문 문장 안의 `**핵심 구**` 는 카드에서 굵게 + 밑줄로 강조되고, 글자 수·금지 표현·수치 검사는 이 표기를 벗기고 한다.

### 4.1 공통 봉투 (3종 공통 필드)

| 필드 | 값 | 필수 |
| --- | --- | --- |
| `schema` / `id` | `<형식 id>/v1` / 고유 id | 모두 |
| `type` | `pre_issue` · `post_issue` · `research` | 모두 |
| `status` | `draft` → `verified` (그 뒤 SOP 상태는 02 문서) | 모두 |
| `language` | 발행 언어 코드(프리셋과 일치) | 모두 |
| `as_of` | **기준 시점** — 이 편이 근거로 삼은 자료의 가장 늦은 시각(ISO 8601 + IANA 시간대) | **모두** |
| `claims[]` | 구분 필드가 달린 주장 목록 → §5 | 수치·고유명사·날짜가 든 문장은 전부 |
| `operator_view` | 운영자 해석 — 자료 요약이 아니라 도메인 지식·경험으로 얹는 관점 | `verified` 에서 필수 |
| `revisions[]` | 수정 이력 → §6 | 발행 뒤 수정 시 필수 |
| `importance` | `major` · `watch` (판정 기준은 02 문서 편성 규칙) | ①② 필수, ③ 해당 없음 |
| `reels` | `{ planned: boolean }` — 이 편을 릴스로 확장할 계획인가 | 선택 |

### 4.2 포맷 ① 이슈 이전 `pre-issue-5` (활성)

**대상 사건**: 기대를 바꿀 사건 — CPI · FOMC · 선거 · 주요 정책 발표 · 예정 연설 등. 선별이 곧 가치다.
**발행 시점**: 기본 **전날**. 복잡한 사건은 그보다 앞서 **배경 설명** 게시물을 먼저 낸다.

| 단 | 키 (`STAGE_KEYS`) | 질문 | 담는 것 |
| --- | --- | --- | --- |
| 1 | `why_it_matters` | 왜 중요한가 | 이 사건이 바꾸는 변수 |
| 2 | `market_expectation` | 현재 시장은 무엇을 예상하는가 | 이미 가격에 담긴 기대 (수치는 출처·기준 시점 필수) |
| 3 | `scenarios` | 결과별 시나리오 | 둘 이상, 각각 조건 → 읽는 법 |
| 4 | `transmission` | 어떤 경로로 자산·업종에 영향을 주는가 | 결과 → 금리·환율·업종 등으로 닿는 길 |
| 5 | `after_checks` | 발표 이후 무엇을 확인할 것인가 | 독자가 직접 확인할 신호와 볼 곳 — **②가 이 항목을 닫는다** |

카드는 표지 + 5단 + 출처 = **7장**. 글자 수 상한(본문 카드 ≤ 220자 등)은 시안 렌더 전 가정값이라 프리셋에 `limits_provisional: true` 로 표시했다.
**정본 스키마**: `packages/domain/src/content/pre-issue.ts` (`pre-issue-5/v1`). 예시: `content/examples/pre-issue/us-midterms-three-repricings.yaml`.

`draft` → `verified` 조건(`verificationBlockers(card)` 가 비어야 함): 일시·시간대 기입, 운영자 해석 기입, 모든 claim 에 출처(url·접근일·원문 인용), 본문 수치마다 claim.
**②와의 연결용 필드(반영됨)**: `scenarios.items[].id`·`after_checks.checks[].id`(안정 키, 선택), 전체 `as_of`, claim 의 §5 구분 필드. `after_checks.closing`(선택)은 독자가 손에 쥘 것을 한 문장으로 닫는 칸이다.

### 4.3 포맷 ② 이슈 이후 `post-issue-4` — 무엇이 달라졌는가

**원칙**: 실제 결과를 **사전 시나리오와 연결**한다. 보도된 사실 · 시장 반응 · 운영자 해석을 섞지 않는다(§5). 충분한 자료를 확보한 **뒤** 낸다.

| 단 | 키 | 질문 | 담는 것 (필드) |
| --- | --- | --- | --- |
| 1 | `result_vs_expectation` | 실제 결과는 예상과 어떻게 달랐나 | `actual_result` (kind `fact`, 1차 출처) · `expectation_gap` (이전 편 2단 `market_expectation` 과의 차이) · **`scenario_outcomes[]`**: 이전 편 시나리오마다 `{ scenario_id, outcome: matched \| partial \| diverged \| unresolved, note }` · **`check_results[]`**: 이전 편 5단의 확인 항목마다 `{ check_id, status: done \| not_available \| dropped, note }` |
| 2 | `market_reaction` | 확인된 시장 반응은 무엇인가 | 관측된 반응만 — kind `market_reaction`, 출처 + **분 단위 기준 시점** 필수. 관측하지 못한 것을 추정으로 채우지 않는다(추정은 해석) |
| 3 | `judgment_update` | 유지되거나 달라진 판단 근거는 무엇인가 | `items[]`: `{ judgment (이전 편의 어떤 판단인지), status: kept \| revised \| dropped, reason, based_on[] (claim id) }`. `revised`·`dropped` 는 §6 수정 이력과 **양방향 연결** |
| 4 | `next_variables` | 다음으로 확인할 변수는 무엇인가 | `items[]`: `{ variable, why, where, when? }` — 연구(③) 스레드 주제로 승격 가능 |

카드 구성 가안: 표지 + 4단 + 출처 = **6장** [미검증 — 첫 편 렌더 뒤 조정].

**이전 ↔ 이후 연결 규칙**
1. 이후 편은 `links.pre_issue_id` 로 이전 편을 가리킨다. 이전 편이 없던 사건이면 비우고 본문에 「사전 시나리오 없음」을 밝힌다(소급해서 만든 것처럼 쓰지 않는다).
2. **이전 편은 발행 뒤 본문을 바꾸지 않는다.** 정정·갱신은 §6 `revisions[]` 로만 한다. 그래서 이후 편이 가리키는 시나리오는 흔들리지 않는다.
3. 이후 편은 이전 편 시나리오 **전부**에 `scenario_outcomes` 로 응답해야 `verified` 가 된다(누락 = 차단). 어느 것에도 맞지 않았으면 `unresolved` 또는 `diverged` 로 솔직하게 적는다.
4. 이전 편 5단 「확인할 것」 항목은 이후 편 `check_results` 로 닫는다. 닫히지 않은 항목은 `next_variables` 로 넘기거나 `dropped` + 이유를 적는다.
5. 대시보드는 쌍(이전 ↔ 이후)을 나란히 보여준다(06 문서, 「이전↔이후 연결 보기」).

**발행 전 자료 확보 조건 (`evidence_ready`, 사람 판단)** — 하나라도 아니면 발행하지 않는다.
- [ ] 결과의 1차 자료가 공개됐고 확인했다
- [ ] 시장 반응을 읽을 만큼 관측 시간이 지났다(몇 시간·몇 거래일인지는 사건마다 운영자가 정하고 사유를 기록 — 하한 숫자는 정하지 않는다)
- [ ] 이전 편 시나리오 전부에 대응이 적혀 있다
- [ ] 보도된 사실 / 시장 반응 / 운영자 해석이 섞이지 않았다

### 4.4 포맷 ③ 트레이딩 연구 `research-5` — 어떻게 판단하고 실행할 것인가

**대상**: 이슈 없는 날의 매매 방법 · 시장 구조 · 리스크 관리 · 판단 과정과 복기, 운영자 자료, 직접 개발한 도구의 소개·공개.
**원칙**: **한 주제를 스레드(thread)로 키운다.** 배포 홍보보다 **게시물 안에서 먼저 가치를 준다** — 도구 편도 사용법·한계가 그 게시물 안에서 끝나야 하고, 배포 안내는 마지막 한 줄 이하(선택)다.

스레드 `thread`: `{ id, topic, posts[] }`. 편 하나 = 스레드의 한 단계(`stage`). 단계는 이 순서로 **발전**하되 한 번에 몰아서 내지 않는다.

| 단 | `stage` | 질문 | 담는 것 (필드) |
| --- | --- | --- | --- |
| 1 | `idea` | 무엇을 왜 보나 | `hypothesis`(가설 한 문장) · `falsifier`(무엇이 보이면 가설이 틀리나) |
| 2 | `conditions` | 언제 쓰고 언제 쓰지 않나 | `applies_when[]` · `not_when[]` · `risk_limits`(리스크 관리 한도, 수치를 쓰면 claim) |
| 3 | `failures` | 어디서 틀렸나 | `cases[]`: `{ case, what_happened, why, what_changed }` — 보통 `basis: experienced` |
| 4 | `tool` | 도구와 사용법 | `name` · `purpose` · `how_to_use[]`(단계) · `inputs` · `outputs` · **`limits`** · **`verified_scope`** · `distribution_note?`(≤ 1줄) |
| 5 | `follow_up` | 후속 검증에서 무엇이 확인됐나 | `tested`(무엇을) · `scope`(기간·표본·시장·비용 가정) · `result_summary` · `still_unknown` · `changes_to_earlier[]`(이전 단계 편 중 바뀐 것 → §6 연결) |

**연구 편 공통 필수 (도구·연구는 한계를 같이 보여준다)**
- `limits` — 적용 조건과 한계. 비어 있으면 `verified` 불가.
- `verified_scope` — **실제로 검증한 범위**: 무엇을 어떤 자료로 어디까지 확인했고, 무엇은 확인하지 않았는가. 성과 수치는 표본·기간·비용 가정과 함께만 쓰고, 「앞으로도 그렇다」로 읽히는 단정은 쓰지 않는다.
- 모든 claim 에 `basis`(§5) — 직접 경험과 조사 내용을 문장 단위로 구분한다.
- `tool` 단계 편은 같은 스레드에 `conditions` 편이 발행됐거나 같은 편 안에 `applies_when`·`not_when` 이 있어야 한다.

**이후(②)와의 연결**: `next_variables` 항목이 연구 스레드 주제가 되면 `links.origin_post_id` 로 이후 편을 가리킨다(느슨한 연결 — 필수 아님).

## 5. 구분 필드 — 사실 / 시장 반응 / 해석 / 시나리오 · 조사 / 직접 경험

모든 주장(claim)은 **두 축**으로 표시한다. 독자에게도 보이게 한다(06 문서 편집기·시안의 구분 표시).

| 필드 | 값 | 뜻 |
| --- | --- | --- |
| `kind` | `fact` 보도된 사실 | 검증 가능한 사실. 출처가 곧 근거 |
| | `market_reaction` 시장 반응 | 관측된 가격·금리·환율 등의 움직임. **관측 시각이 생명** |
| | `interpretation` 운영자 해석 | 사실 위에 얹은 관점. 틀릴 수 있음을 전제로 쓴다 |
| | `scenario` 시나리오 | 조건 → 읽는 법. 예측이 아니다. 확률 숫자를 붙이지 않는다 |
| `basis` | `researched` 조사 | 외부 자료에서 가져온 내용 |
| | `experienced` 직접 경험 | 운영자가 직접 해 보고 관측한 내용(도구 사용·매매 복기 등) |
| `as_of` | 기준 시점 | 필수. 자료의 시점(사실·시장 반응) 또는 작성 시점(해석·시나리오) |
| `drafted_by` | `operator` · `assistant` | 자동 초안이면 `assistant`. 사람이 저장해야 `operator` 로 바뀐다 |

**종류별 필수 필드** (비어 있으면 `verified` 불가 — 스키마가 강제)

| `kind` / `basis` | 필수 |
| --- | --- |
| `fact` / `researched` | `source`(`url` · `publisher` · `accessed_at` · `quote` 원문 그대로 · `tier` primary \| major_media \| other) · `as_of` · **사람 확인 기록**(`verified_by`·`verified_at`) |
| `market_reaction` / `researched` | 위와 같고 `as_of` 는 **분 단위 + 시간대**. 게시 직전 재확인 표시 |
| `fact` / `experienced` | `experience`(`what` 무엇을 했나 · `when` · `data_location` 재확인할 수 있는 자료 위치) |
| `interpretation` | `as_of` · `based_on[]`(이 해석이 서 있는 claim id — 사실 없는 해석 금지) · basis 가 `experienced` 면 `experience` |
| `scenario` | `condition` · `as_of` · 같은 편에 시나리오가 **둘 이상** |

**규칙**
1. 한 문장에는 `kind` 를 하나만 준다. 사실과 해석이 한 문장에 섞이면 둘로 쪼갠다.
2. 해석·시나리오는 `based_on` 으로 사실에 닿아 있어야 한다. 닿지 않으면 「근거 없는 주장」으로 검수에서 막는다.
3. 확률·목표가 같은 **수치 단정 필드를 만들지 않는다**(`probability` 필드 없음).
4. 직접 경험은 조사 내용처럼 보이게 쓰지 않는다 — 「내가 해 보니」와 「자료에 따르면」은 화면에서도 다르게 보인다.
5. 편 전체의 `as_of` 는 claim 들의 `as_of` 중 가장 늦은 값 이상이어야 하고, 표지 푸터에 표시한다.

## 6. 수정 이력 — 정정 이유를 남긴다

발행한 편의 본문은 **덮어쓰지 않는다.** 바꾸면 이력이 쌓이고, 독자에게는 이유가 보인다.

`revisions[]` 한 건:

| 필드 | 값 | 필수 |
| --- | --- | --- |
| `at` / `by` | 수정 시각 / 수정자 | 모두 |
| `change_kind` | `correction` 사실 오류 정정 · `update` 새 자료로 판단이 바뀜 · `clarification` 표현만 명확화 | 모두 |
| `affected` | 바뀐 claim id 또는 필드 경로 | 모두 |
| `before` / `after` | 바뀌기 전·후 문구 | 모두 |
| `reason` | **수정 이유**(사람이 읽는 문장) | **모두** |
| `reader_note` | 독자에게 보이는 정정 문구(캡션·카드 하단) | `correction` · `update` 필수 |
| `follow_up_post_id` | **후속 게시물**에서 이유를 설명한 편 | `update` 필수(발행 전이면 `follow_up_due` 날짜) |

- `update`(분석이 달라짐)는 조용히 고치지 않는다. 이후 편 `judgment_update` 또는 연구 `follow_up` 에서 **왜 달라졌는지**를 설명하고, 이력과 서로 연결한다.
- 수정하면 02 문서 「승인 무효」 규칙대로 기존 승인이 풀리고 재검수를 거친다.
- 이력은 지우지 않는다. 대시보드는 편마다 이력 목록을 보여준다(06 문서).
